## 2. Backup Policy Options

### Option A - Conservative

- Database plus uploads backup frequency: every 12 hours.
- Freshness `WARNING`: latest structurally valid recovery set older than 18 hours.
- Freshness `CRITICAL`: latest structurally valid recovery set older than 30 hours, or required artifact missing.
- Checksum verification frequency: after every backup and once daily.
- Restore rehearsal frequency: monthly, plus after major schema/storage changes and before major pilot expansion.
- Retention approach: 14 daily recovery sets, 8 weekly anchors, 6 monthly anchors.
- Operational burden: high; more storage, more operator review, more frequent evidence capture.
- Pilot suitability: strong protection, heavier than the current pilot may need.
- Risk tradeoff: best freshness posture; higher alert fatigue and storage-growth pressure.

### Option B - Balanced / Recommended

- Database plus uploads backup frequency: daily.
- Freshness `WARNING`: latest structurally valid recovery set older than 30 hours.
- Freshness `CRITICAL`: latest structurally valid recovery set older than 48 hours, or required artifact missing.
- Checksum verification frequency: after every backup; daily if backups are generated by a separate process and checksum verification evidence is not attached.
- Restore rehearsal frequency: monthly during pilot, plus after major schema/storage/backup-system changes and before larger pilot expansion.
- Retention approach: 7 daily recovery sets, 4 weekly anchors, 3 monthly anchors.
- Operational burden: moderate; practical for a pilot while keeping recovery evidence current.
- Pilot suitability: recommended for current FixZone pilot maturity.
- Risk tradeoff: reasonable recovery freshness without turning operations into a constant manual exercise.

### Option C - Lower Overhead

- Database plus uploads backup frequency: every 48 hours.
- Freshness `WARNING`: latest structurally valid recovery set older than 60 hours.
- Freshness `CRITICAL`: latest structurally valid recovery set older than 84 hours, or required artifact missing.
- Checksum verification frequency: after each backup only.
- Restore rehearsal frequency: quarterly, plus after major schema/storage/backup-system changes.
- Retention approach: 7 recent recovery sets, 4 weekly anchors, 2 monthly anchors.
- Operational burden: lower; less storage and fewer routine checks.
- Pilot suitability: acceptable only for very low-volume/non-critical pilot windows.
- Risk tradeoff: larger potential data-loss window and slower detection of backup-process drift.

None of these options is approved by this document.

## 3. Recommended Pilot Policy

Recommended policy:

```text
PROPOSED - OPERATOR APPROVAL REQUIRED: Option B, Balanced.
```

This is not a formal SLA, RPO, or RTO.

Rationale:

- FixZone stores citizen reports, provider work evidence, completion governance decisions, organization workflow state, audit/activity records, and protected evidence metadata.
- Daily coordinated database-plus-uploads backups are a practical pilot posture because evidence and database rows must remain recoverable together.
- The current platform has one successful recovery rehearsal and a verified persistent upload mount, but backup scheduling, alert routing, retention, and recurring restore cadence are not yet mature enough for aggressive automation.
- A 30-hour warning and 48-hour critical threshold catches missed daily backups without forcing emergency escalation for minor timing drift.

## 4. Independent Frequencies

Backup frequency:

- Proposed: daily coordinated PostgreSQL dump plus uploads archive.

Host monitor frequency:

- Proposed: every 15 minutes after scheduling is approved.
- Reason: API, mount, disk, upload consistency, and backup visibility are lightweight checks and should detect operational drift promptly.

Checksum verification frequency:

- Proposed: after every backup.
- If backup and monitor are separated, run checksum verification through a separate daily verification job or after-backup hook rather than every 15-minute monitor cycle.

Restore rehearsal frequency:

- Proposed: monthly during pilot, after major schema changes, after storage/mount changes, after backup-system changes, and before major pilot expansion.

These frequencies are independent. Backup frequency is not host-monitor frequency, checksum verification frequency is not restore-rehearsal frequency, and restore rehearsal is not a routine monitor cycle.

## 5. Backup Freshness State Contract

`HEALTHY`:

- Latest recovery set is structurally valid and within the configured warning threshold.

`WARNING`:

- Latest structurally valid recovery set is older than the warning threshold but younger than the critical threshold.
- Checksum manifest exists but checksum verification evidence is incomplete for the latest backup under a policy that expects after-backup verification.

`CRITICAL`:

- Latest recovery set is older than the critical threshold.
- Required artifact is missing or zero-size.
- Checksum verification fails.
- Recovery-set directory cannot be read when it should be readable by the monitor.

`UNKNOWN`:

- Freshness thresholds are not configured.
- Latest recovery set cannot be safely determined.
- Backup verification metadata is unavailable.
- Restore rehearsal evidence is not visible to the routine monitor.

Override rules:

- Missing or invalid required artifact overrides freshness age and is `CRITICAL`.
- Checksum failure is `CRITICAL`.
- Checksum not run is `UNKNOWN` until an after-backup verification policy is approved; after approval, it should become `WARNING` if stale verification evidence persists past one monitor cycle.
- Restore rehearsal age should remain a separate `restore_rehearsed` or `restore_rehearsal` signal. It should not automatically make backup freshness `CRITICAL`, because a fresh backup can be structurally present even if restore rehearsal evidence is old.

## 6. Checksum Verification Policy

Options evaluated:

- Every monitor cycle: strongest continuous validation, but can create unnecessary disk I/O as archives grow and may lengthen the frequent monitor runtime.
- After every backup: best match to backup creation; verifies each recovery set once when it is created.
- Once daily: practical if backups are less frequent or verification is separate, but may lag after backup creation.
- Separate verification schedule: flexible, but introduces another job and missed-run surface.

Recommended:

```text
PROPOSED - OPERATOR APPROVAL REQUIRED: verify checksums after every backup.
```

If the backup process and monitor remain separate, record checksum verification evidence beside the recovery set and let the host monitor read that safe metadata. Do not run expensive checksum verification every 15 minutes by default.

## 8. Alert Routing Policy

`HEALTHY`:

- Structured log.
- Update latest-status record.
- No human alert.

`WARNING`:

- Operator-visible status.
- Email notification after email delivery is approved.
- Reminder if unresolved beyond the configured reminder interval.

`CRITICAL`:

- Immediate operator alert.
- Email after delivery approval.
- Future SMS/push escalation after provider approval.
- Open incident workflow and stop planned releases.

`UNKNOWN`:

- Operator-visible configuration/investigation state.
- No emergency escalation on first occurrence.
- Escalate if persistent beyond an approved period, such as two hours or eight consecutive 15-minute checks.

No email, SMS, push, paid provider, or citizen/provider notification routing is activated by this document.

## 9. Alert Deduplication

Event identity:

- `check_key`.
- `state`.
- normalized summary.
- affected environment.

First occurrence:

- Emit an alert when a check enters `WARNING`, `CRITICAL`, or persistent `UNKNOWN` from `HEALTHY` or from no prior state.

Repeat reminder:

- Suppress identical alerts during the reminder window.
- Suggested unapproved reminder windows: `WARNING` every 6 hours, `CRITICAL` every 30 minutes, persistent `UNKNOWN` every 2 hours.

State escalation:

- Always alert on escalation, such as `HEALTHY -> WARNING`, `WARNING -> CRITICAL`, or `UNKNOWN -> CRITICAL`.

Recovery:

- Emit one recovery notification when a previously non-healthy check returns to `HEALTHY`.
- Include previous state and duration if state history is available.

State downgrade:

- Emit one update when `CRITICAL -> WARNING` or `CRITICAL -> UNKNOWN`, but avoid declaring recovery until `HEALTHY`.

## 10. Missed-Run Detection

Required heartbeat fields:

- last monitor execution timestamp;
- last completed monitor state;
- last successful run;
- last `WARNING`;
- last `CRITICAL`;
- last `UNKNOWN`;
- last alert emission time by event identity.

Options:

- Host-local state file: smallest and safest first step; no backend schema or endpoint required.
- External watchdog: strong missed-run detection, but requires external service setup.
- Backend operational-status ingestion endpoint: useful later; requires auth, schema, API, and replay/dedup design.
- External uptime monitor: good for API liveness, weaker for host-level backup/mount internals unless it can ingest script output.

Recommended V1 design:

```text
PROPOSED - OPERATOR APPROVAL REQUIRED: host-local JSON state file plus scheduler logs.
```

Missed-run detection contract:

- Scheduler writes or rotates logs.
- Script writes a latest-status JSON file only after a completed run.
- A lightweight watchdog checks file modified time.
- If no completed run is recorded within two expected intervals plus grace, mark monitor heartbeat `WARNING`.
- If no completed run is recorded within four expected intervals plus grace, mark monitor heartbeat `CRITICAL`.

This is not implemented by this document.

## 11. Alert Delivery Architecture

Options:

1. Structured host logs only: simplest, immediately compatible, weakest operator visibility.
2. Host-local JSON state file: small, safe, useful for deduplication and missed-run detection.
3. Backend operational-status ingestion endpoint: better dashboarding, requires secure ingestion and schema/API design.
4. Dedicated `OperationalAlert` database model: strong long-term audit trail, but adds migrations and application surface.
5. Email delivery: useful for operators after SMTP ownership and templates are approved.
6. External monitoring service: strong uptime/alerting, may add cost/configuration and must not expose secrets.

Recommended first implementation:

```text
Host-local JSON state file plus structured logs.
```

Do not mix infrastructure alerts into citizen/provider notification streams. A dedicated operational event model can be considered later for Super Admin operational visibility.

## 12. Scheduler Options

Cron:

- Pros: simple, available, familiar.
- Cons: weaker service lifecycle visibility, missed-run detection must be added separately.

Systemd timer:

- Pros: reliable, persistent across deploys, good logs through journald, explicit service unit, better missed-run visibility.
- Cons: requires VPS/systemd access and operator setup.

Dokploy schedule:

- Pros: close to application operations if supported.
- Cons: may be tied to application/deploy lifecycle and may not have host-level permissions needed for Docker/mount checks.

External monitor:

- Pros: strong alerting and independent availability.
- Cons: may not see local Docker mount identity or recovery-set filesystem without an agent.

Recommended scheduler:

```text
PROPOSED - OPERATOR APPROVAL REQUIRED: systemd timer on the Hostinger Ubuntu VPS.
```

Do not configure it until separately authorized.

## 13. Retention Options

Option 1 - Balanced pilot retention:

- Keep 7 daily recovery sets.
- Keep 4 weekly anchors.
- Keep 3 monthly anchors.
- Require manual approval before deletion.
- Suitable for current pilot if storage growth is monitored.

Option 2 - Conservative pilot retention:

- Keep 14 daily recovery sets.
- Keep 8 weekly anchors.
- Keep 6 monthly anchors.
- Higher storage cost and review burden.
- Better recovery history for a busy pilot.

Option 3 - Lower overhead retention:

- Keep 7 recent recovery sets.
- Keep 4 weekly anchors.
- Keep 2 monthly anchors.
- Lower storage usage.
- Higher risk if a latent issue is discovered late.

Recommended retention:

